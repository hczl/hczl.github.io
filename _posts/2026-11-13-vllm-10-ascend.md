前九篇都在 RTX 4090 上，第九篇用了两张。这一篇换一种芯片：华为昇腾 910B1，一张卡标称 64 GB HBM。模型、服务参数、测试脚本和前几篇完全一样，只换了硬件和那一层适配代码。

行为以 vLLM 0.32.0 加 vllm-ascend 0.32.0rc1 为准。机器是一台 8 卡的昇腾服务器，CANN 9.2.1，torch 2.10.0 配 torch-npu 2.10.0.post7，Python 3.11，模型还是 Qwen3-8B（bf16），和前九篇是同一份权重。服务参数也照搬：`--max-model-len 32768`，开前缀缓存，`--gpu-memory-utilization` 用默认的 0.92。

对照组是第九篇那台机器上的单卡 4090 数据，同一批 prompt、同一个脚本。

## 先看一个缩小的例子

两张卡上 vLLM 划显存的算法是同一套：按 `--gpu-memory-utilization` 算出预算，减掉权重，减掉跑一次前向时量到的显存峰值，剩下的全给 KV Cache。输入换成一张大得多的卡，这个减法的结果会怎么变？

{% include bar-demo.html id="ascend-startup-memory" caption="图 1：同一条启动命令在两种卡上把显存一项项分出去。条的长度按同一个比例尺，数字都来自两边的启动日志" %}

要点是权重那一段在两张卡上几乎一样长：同一个模型，参数量不变，占的显存也不变。预算多出来的 34 GiB 没有别的去处，原样落在 KV 上。于是 KV 差了 7.4 倍，而权重只差 1%。下面逐项看实测。

## 装环境

版本要配套：vllm-ascend 0.32.0rc1 对应 vLLM 0.32.0、CANN 9.2.1、torch 2.10.0、torch-npu 2.10.0.post7，另外要装 triton-ascend 3.6.0.post2。在已经装好 CANN 的机器上，关键是 vLLM 只装 Python 部分，设备代码交给 vllm-ascend：

```bash
pip install torch==2.10.0 torch-npu==2.10.0.post7
VLLM_TARGET_DEVICE=empty pip install --no-build-isolation --no-binary vllm vllm==0.32.0
pip install triton-ascend==3.6.0.post2 vllm-ascend==0.32.0rc1
```

两个坑。一是 `--no-binary vllm` 不能省：PyPI 上的 aarch64 vllm wheel 是给 CUDA 编的，pip 一拿到它，`VLLM_TARGET_DEVICE` 就不起作用了；装对了版本串是 `0.32.0+empty`。二是启动时报 `No module named 'fla_npu'`：vllm-ascend 无条件 import 这个线性注意力算子包，跑 Qwen3-8B 也要它，但它不在 PyPI 上，要从上游项目的 release 页面下载对应架构的 wheel，校验 sha256 后装进同一个环境。

## 启动：显存怎么分

启动命令和前几篇一字不差：

```bash
vllm serve Qwen/Qwen3-8B --max-model-len 32768 --enable-prefix-caching
```

日志里的关键几行和 4090 对照：

| | RTX 4090 | Ascend 910B1 |
| --- | ---: | ---: |
| 框架看到的整卡显存 | 23.52 GiB | 60.96 GiB |
| 0.92 的预算 | 21.64 GiB | 56.08 GiB |
| 权重（`Model loading took`） | 15.54 GiB（含非框架部分） | 15.29 GiB |
| 一次前向的显存峰值增量 | 0.62 GiB | 0.20 GiB |
| KV Cache（`Available KV cache memory`） | 5.48 GiB | 40.56 GiB |
| KV 容量 | 39,920 token | 295,296 token |
| block 数 | 2,495 | 2,307 |
| 一个 block 多少 token | 16 | 128 |
| 图捕获占用 | 0.23 GiB | 0.68 GiB |

每个 token 的 KV 大小两边一样，还是第三篇那个式子：

$$
2 \times 36 \times 8 \times 128 \times 2 = 147456 \text{ 字节} = 144 \text{ KiB}
$$

40.56 GiB 除以 144 KiB 正好是 295,296 个 token，和日志里的容量对得上。日志这一行的设备名跟着变了，写的是 `NPU KV cache size: 295,296 tokens, Maximum concurrency for 32,768 tokens per request: 9.01x`：能同时放下 9 条满长度的请求，4090 上这个数是 1.2。KV 张量的摆法日志里也说了一句，`Using LBNHC KV cache layout`，层在最外层，每层一块缓冲再切成 K、V 两个视图。

## block 为什么是 128

4090 上一个 block 存 16 个 token，这是 vLLM 的默认值。昇腾上启动时多了两行：

```text
Block size is set to 128 if prefix cache or chunked prefill is enabled.
Setting kv cache block size to 128 for CUSTOM backend(s).
```

第一行是 vllm-ascend 自己加的规则：只要开着前缀缓存或分块 prefill，block 就改成 128。本文的配置两个都开着，所以走的是这一条。第二行是框架按 attention 后端的要求选 block 大小的那一步，昇腾的 attention 算子只接受 128 个 token 的 block，结果也是 128。block 大了 8 倍，但每个 token 还是 144 KiB，所以一个 block 从 2.25 MiB 变成 18 MiB，block 的数量反而比 4090 还少一点（2,307 对 2,495），这只是巧合：KV 大了 7.4 倍，单块也大了 8 倍。

block 变大，最直接的影响在前缀缓存上。第六篇讲过，缓存是按满 block 存的，不满一块的尾巴存不进去：

{% include kv-demo.html id="ascend-block-128" caption="图 2：同一段 prompt，block 是 16 个 token 和 128 个 token 时各能命中多少。一格 8 个 token，比例和实测一致" %}

实测的 6 轮对话，和第六篇是同一段：

| 轮次 | prompt token | 4090 命中 | 910B1 命中 | 命中率差 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 307 | 0 | 0 | — |
| 2 | 7,219 | 7,200 | 7,168 | 0.4% |
| 3 | 15,421 | 7,200 | 7,168 | 0.2% |
| 4 | 15,536 | 15,408 | 15,360 | 0.3% |
| 5 | 15,607 | 15,520 | 15,488 | 0.2% |
| 6 | 15,680 | 15,600 | 15,488 | 0.7% |

每一轮昇腾都少命中几十个 token，因为命中必须落在 128 的整数倍上。prompt 越长这点损失占比越小，一万五千多个 token 时不到 1%，对应的首 token 时间是 0.13 到 0.14 秒。所以这是个可以记住但不用担心的差别。

### `--block-size` 被改成 128

既然 block 大小变了，自然想试试能不能调回去。结论是：**在本文的配置下（开着前缀缓存，分块 prefill 默认也开着），这个参数传什么都会被改成 128，也不会报错。**

分别用 `--block-size 16`、`--block-size 64`、`--block-size 256` 各起了一次服务，三次都正常启动，而且三次的 KV 容量、block 数、6 轮命中、单条和 16 并发的吞吐，与不传这个参数时逐位相同，都是 295,296 个 token、2,307 块。`/metrics` 里能看到这件事的痕迹：`user_specified_block_size="True"` 而 `block_size="128"`——框架记下了用户确实传了值，然后用的还是 128。改写发生在上面那行 `Block size is set to 128 if prefix cache or chunked prefill is enabled.`，它不管这个值是不是用户自己传的。

只有前缀缓存和分块 prefill 两个都关掉，用户传的值才会留下来，交给后面按 attention 后端选 block 的那一步检查。那时 16 和 64 会报错 `No common block size for 16 (CUSTOM: [128])`（64 同理），256 会保留下来，再拆成两个 128 交给算子。这种情况本文测不到：`max_num_batched_tokens` 默认是 2048，比 `--max-model-len 32768` 小，分块 prefill 关不掉。

## 并发和吞吐

每条请求约 1,815 个 token 输入、256 个 token 输出，并发从 1 加到 64：

{% include figure.html src="/assets/images/vllm-10-ascend/01-concurrency.png" alt="并发 1 到 64 时，单卡 910B1、两卡 TP=2 和单卡 4090 的总吞吐与单条 decode 速度曲线" caption="图 3：左边是总吞吐，右边是每条请求的 decode 速度中位数。灰色曲线上的数字是这一档里发生的抢占次数" %}

| 并发 | 4090 总吞吐 | 910B1 总吞吐 | 4090 抢占 | 910B1 抢占 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 55.6 | 65.6 | 0 | 0 |
| 4 | 183.6 | 221.5 | 0 | 0 |
| 16 | 469.9 | 563.0 | 0 | 0 |
| 32 | 460.9 | 789.6 | 2 | 0 |
| 64 | 460.2 | 960.3 | 6 | 0 |

单条请求时 910B1 每秒 68.0 个 token，4090 是 58.0，快 17%。真正拉开差距的是高并发：4090 在 16 并发之后就不涨了，第七篇分析过原因，KV 不够用，32 并发抢占 2 次、64 并发抢占 6 次，被抢的请求要重算，吞吐卡在 460 左右。910B1 有 7.4 倍的 KV，64 并发时也只用掉 45%，一次抢占都没有，吞吐一路涨到 960。

一条 16,087 个 token 的长 prompt，prefill 时间 1.51 秒，4090 是 2.21 秒。

### 把容量压到和 4090 一样

上面的差距里，有多少是芯片算得快，有多少只是显存大？把 KV 容量强行压到和 4090 一个量级就能分开看。用 `--num-gpu-blocks-override 312` 把容量设成 312 × 128 = 39,936 个 token，和 4090 的 39,920 相差 16 个 token，再跑第七篇那组会触发抢占的回放：4 个会话、每轮输出 2,000 个 token、错开 0.5 秒启动。

结果是抢占 1 次，和 4090 在同样回放下的 1 次一模一样。`/metrics` 里 `vllm:num_preemptions_total` 从 0 变成 1。抢占的策略也没变，还是第七篇说的重算：被抢的请求释放掉全部 block，已算 token 数清零，回到等待队列的队首。

也就是说，高并发那一段的优势基本来自显存容量，而不是调度上有什么不同——调度器本来就是同一个，昇腾这边没有替换它。

### 八个会话的回放

再跑一遍第一篇那个编程智能体：8 个会话每隔 3 秒启动一个，每个 6 轮，每轮最多输出 256 个 token。

| | 4090（第九篇） | 910B1 | 910B1，容量压到 39,936 |
| --- | ---: | ---: | ---: |
| 全部跑完 | 66.2 s | 32.8 s | 39.8 s |
| KV 占用峰值 | 99.4% | 18.1% | 98.4% |
| 最慢的一轮 | 14.8 s | 2.1 s | 7.0 s |

默认容量下昇腾这一轮只用掉 18% 的 KV，最慢的一轮 2.1 秒；4090 的 KV 被占满，有一半会话在等待队列里排队，最慢的一轮 14.8 秒。把容量压到和 4090 一样之后，KV 同样被占满（98.4%），最慢的一轮变成 7.0 秒，但总时间仍是 39.8 秒。容量和速度各占一部分，这组对照把两者分开了。

## 图模式和 `--enforce-eager`

第二篇在 4090 上测过 `--enforce-eager`：不编译、不捕获图，decode 慢 2% 到 22%（上下文 307 个 token 时每秒 58.5 对 48.0，上下文一万五千多时只差 2% 到 4%）。同样的开关在昇腾上要严重得多：

{% include figure.html src="/assets/images/vllm-10-ascend/02-graph-vs-eager.png" alt="默认图模式与 --enforce-eager 在 910B1 上的对比：decode 吞吐差 5.7 倍，16k prefill 时间几乎相同" caption="图 4：910B1 上默认启动和 --enforce-eager 的对比。decode 差 5.7 倍，16k prefill 几乎不差" %}

单条请求（约 1,815 个 token 的 prompt）的 decode 从每秒 68.0 个 token 掉到 12.0 个，是 1/5.7。并发 64 时总吞吐从 960.3 掉到 516.6。而一条 16,087 个 token 的长 prompt，prefill 图模式 1.51 秒，eager 1.53 秒，几乎没有差别。

第八篇在 4090 上抓 profile 看过原因：decode 每一步只算一个 token，一层里的计算量很小，时间主要花在把几百个算子一个个发下去，而捕获成图之后一整步只要回放一次。昇腾上为了看清差距为什么大这么多，另外用 profiler 抓了一次单条请求的 decode。这次是新起的一组服务，接口报的 prompt 是 1,459 个 token，和上面那组的 1,815 对不上，原因没有查清；不开 profiler 时 decode 是每秒 68.43 对 13.44 个 token，差 5.1 倍，折合每步 14.6 毫秒对 74.4 毫秒。下面的数字都来自这一组：

- **设备上的计算几乎没变。** 一步 decode 里所有算子在设备上的执行时间加起来，图模式 14.55 毫秒，eager 14.97 毫秒，只差 3%。大头都是同一批矩阵乘，两边都是 145 次、约 12.06 毫秒。eager 下有几个小算子没有像图模式那样融合在一起，但多出来的设备时间只有 0.5 毫秒左右。
- **多出来的时间是设备在空等。** eager 下每一步，设备大约有 72 毫秒什么也没做（开着 profiler 量的，profiler 本身会让 eager 每步再慢 10 毫秒左右），图模式只有 0.24 毫秒。
- **空等的原因是 host 下发跟不上。** eager 每一步要由 host 一个一个地下发约 460 个算子，设备上相邻两个算子之间的间隔中位数是 132 微秒，460 次乘起来就是六十毫秒上下。图模式每一步 host 只单独下发 61 次，其余三百多个算子不再单独下发，而是随每步一次的图执行提交下去。下发调用本身平均只占每次间隔里的 6 微秒左右，剩下的时间花在 host 侧的哪一段，这次没有再拆。

所以昇腾上 eager 慢，不是算子变慢了，而是设备每算完一个算子，都要等 host 把下一个发过来，而这段等待比算子本身还长。图模式把一步里的大部分算子一次交给设备，这段等待就没了。

prefill 上也看得到同样的开销，只是比例小得多。同一组里 1,459 个 token 的首 token 时间，图模式 0.122 秒，eager 0.180 秒，eager 慢了将近一半，而这一步在设备上的计算只多了 4%。16k 那条 prefill 两边几乎一样，那次没有抓 profile。

默认启动时捕获的图不止一张。日志显示引擎按 35 种批大小各捕获了一遍，分别是 1、2、4，然后从 8 到 248 每隔 8 一档，最后是 256；而且每种尺寸都捕获了两遍，一遍整图、一遍分段的。这就是下一节启动要等那么久的主要原因。

## 第一次启动要等三分半

在 4090 上，第二篇记过冷启动和热启动的差别：第一次启动要编译，之后有缓存就快了。昇腾上这件事更明显，而且不只影响启动，还影响第一条请求。

做了一组受控实验：清空编译缓存启动一次，紧接着用完全相同的命令再启动一次。

{% include figure.html src="/assets/images/vllm-10-ascend/03-compile-cache.png" alt="清空编译缓存和缓存已热时，启动耗时 211.5 秒对 139.2 秒，第一条请求的首 token 时间 22.7 秒对 0.21 秒" caption="图 5：同一条命令连着启动两次。右图是对数坐标" %}

- 清空缓存：从进程启动到 `/health` 返回要 **211.5 秒**，之后第一条请求的首 token 时间是 **22.7 秒**。
- 缓存已热：启动 **139.2 秒**，同一条请求 **0.21 秒**。
- 两次的稳态 decode 都是每秒 68 个 token，一点不差。

也就是说，第一次跑的时候，启动多花了 72 秒，还有 22 秒的编译摊在了第一条请求上——服务已经回 `/health` 了，看上去准备好了，实际第一个用户要等二十多秒。压测前一定要先打一条预热请求，否则第一条的数字毫无意义。

第一次启动要做两件编译：torch.compile（包括 AOT 编译）和 Triton 内核编译。结果放在两个地方：`VLLM_CACHE_ROOT` 下的 `torch_compile_cache`（一个 10 位哈希命名的目录，加上同级的 `torch_aot_compile/<64 位哈希>`，合计 4.6 MB），以及 `TRITON_CACHE_DIR`（7.0 MB）。这两份缓存是跨进程复用的：后面每个实验阶段都是新起的进程，首条请求都是 0.2 秒左右。

至于热启动为什么还要 139 秒：上一节那 70 种图不在这两份缓存里，每次启动都要重新捕获，捕获结果不落盘。

## 两张卡：TP=2

最后把第九篇的 TP=2 也跑一遍。这台机器上 8 张卡两两之间都是 HCCS 直连，不像第九篇那两张 4090 只能走 PCIe。

| | 单卡 | TP=2（每卡） |
| --- | ---: | ---: |
| 权重 | 15.29 GiB | 7.66 GiB |
| KV Cache | 40.56 GiB | 47.79 GiB |
| KV 容量 | 295,296 token | 695,936 token |
| 单条 decode | 68.0 token/s | 75.5 token/s |
| 64 并发总吞吐 | 960.3 token/s | 1113.8 token/s |
| 16k prefill | 1.51 s | 1.39 s |

切分方式和第九篇完全一样：每张卡放一半权重，每层 8 个 KV 头分成每卡 4 个，于是每张卡每个 token 是 72 KiB。695,936 × 72 KiB 正好是 47.79 GiB，对得上。容量涨到 2.36 倍，原因也和第九篇一样：省下的权重显存给了 KV，每个 block 在单卡上又只有一半大。

通信这边，两卡之间的 all-reduce 走 HCCL，和第九篇的 NCCL 对比（bf16，两进程，CPU 计时）：

| 数据量 | 910B1 / HCCS | 带宽 | 4090 / PCIe | 带宽 |
| ---: | ---: | ---: | ---: | ---: |
| 8 KB | 126.4 µs | 0.06 GB/s | 50.6 µs | 0.16 GB/s |
| 1 MB | 125.8 µs | 8.33 GB/s | 93.2 µs | 11.25 GB/s |
| 16 MB | 939.4 µs | 17.86 GB/s | 1153.5 µs | 14.54 GB/s |
| 64 MB | 3657.0 µs | 18.35 GB/s | 4479.7 µs | 14.98 GB/s |

两边的形状不一样：小数据量时昇腾这边的固定开销明显更高（8 KB 时 126 µs 对 50 µs），一直到 1 MB 都几乎是同一个时间，说明这一段完全由固定开销主导；数据量大了以后反过来，64 MB 时昇腾的带宽高 22%。decode 一步里每层要做两次 all-reduce，每次的数据量是 batch 里的 token 数乘隐藏层维度，batch 小的时候正好落在固定开销主导的那一段，这也解释了为什么 TP=2 在单条请求上只快了 11%。
