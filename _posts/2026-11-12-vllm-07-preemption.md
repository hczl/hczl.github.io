第一篇的最后说，几个会话同时跑时，前两次实验都没有出现抢占，第三次让每轮强制输出 2000 个 token，4 个会话就出现了一次。第四篇说，请求留在等待队列里，可能是这一步的预算已经分完，也可能是 KV Cache 不够，KV Cache 被占满时调度器怎么做放到这一篇。这一篇就看第三次实验：一条请求为什么在有空闲 block 的时候也进不了运行队列，这次抢占为什么还是发生了，被抢占的请求交出了什么、保留了什么，恢复时又重算了多少。

行为以 vLLM 0.32.0 为准。实验是第一篇那台机器、那个服务，`--gpu-memory-utilization` 0.92，KV Cache 是 2494 个 block，前缀缓存开着，调度策略是默认的先到先服务。同样的实验跑了两次，第二次打开了 DEBUG 日志，两次的过程几乎一样，下面的数字除特别说明外都来自第一次。

## 先看一个缩小的例子

实测的数字比较大，先把规则放到一个很小的例子里走一遍：KV Cache 只有 8 个 block，A、B、C 三个请求的 prompt 各要 3 个 block，decode 时每一步正好写满一个 block。规则和 vLLM 0.32.0 一样，数字只是示意，可以按“下一步”一步步看。

{% include kv-demo.html id="preempt" caption="图 1：抢占和恢复的示意。格子是 KV Cache 里的 block，虚线框是空闲的 block，里面还写着名字的是挂着哈希、仍能被命中的" %}

这个例子里有两条规则。第一条是准入：等待队列里的请求要进运行队列，空闲 block 得放得下它的整段 prompt，放不下就整条不进，所以 C 有 2 个空闲 block 也进不来。第二条是抢占：准入时只估算了 prompt，没有估算还要输出多少 token，运行中的请求 decode 时分不到新 block，调度器就把运行队列里最后进来的请求打断，收回它的 block，让它回到等待队列；等它再被调度时，重新查前缀缓存，命中的 block 直接用，只重算没命中的尾部。

下面的实测是同样的过程，只是 block 有 2494 个：会话 2、3 的第 3 轮像 C 一样有空闲 block 也进不来；第 4 轮里，会话 0 和会话 1 的第 4 轮就是 A 和 B，被抢占的是后进来的会话 1，恢复时它开头的 block 都还在，只重算了尾部。

## 例子：4 个会话，每轮输出 2000 个 token

还是第一篇那个编程智能体，4 个会话每隔 0.5 秒启动一个，每个会话跑 4 轮，每轮都正好输出 2000 个 token。prompt 和平时一样，第 2 轮读进文件后涨到几千到八千多 token，第 3、4 轮涨到一万五到两万一。实验期间每 0.5 秒抓一次 `/metrics`，每条请求结束时也抓一次。

16 条请求的情况，时间从第一条请求发出时算起：

| 请求 | prompt token | 发出 | 首 token | 结束 | decode 用时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 会话 0 第 3 轮 | 19,011 | 86.0 s | 87.7 s | 135.3 s | 47.6 s |
| 会话 1 第 3 轮 | 14,923 | 86.0 s | 89.0 s | 136.3 s | 47.3 s |
| 会话 2 第 3 轮 | 14,746 | 86.1 s | 137.4 s | 184.5 s | 47.1 s |
| 会话 3 第 3 轮 | 15,720 | 87.0 s | 139.3 s | 186.1 s | 46.8 s |
| 会话 0 第 4 轮 | 21,072 | 136.3 s | 187.7 s | 234.1 s | 46.4 s |
| 会话 1 第 4 轮 | 16,984 | 137.3 s | 189.8 s | 258.4 s | **68.6 s** |
| 会话 2 第 4 轮 | 16,807 | 185.5 s | 236.6 s | 285.3 s | 48.7 s |
| 会话 3 第 4 轮 | 17,779 | 187.1 s | 260.9 s | 304.4 s | 43.5 s |

前两轮 prompt 短，8 条请求都是一发出就开始算，表里没有列。从第 3 轮起，每次只有两条请求在跑，后到的请求在等待队列里等，表里有 6 条首 token 时间在 51 到 74 秒之间。抢占只有一次，被抢占的是会话 1 的第 4 轮，它的 decode 比同批的请求多用了 20 秒左右。

被抢占的是哪一条，`/metrics` 里能直接看出来。`vllm:num_preemptions_total` 是抢占的总次数；`vllm:request_num_preemptions` 是一个直方图，每条请求结束时把它被抢占的次数记一次。这个直方图的桶从 1 开始，抢占 0 次和 1 次都落进 `le="1"` 的桶，要看它的 `_sum`。按结束的先后看每条请求结束时抓到的值：会话 0 第 4 轮结束时，`vllm:num_preemptions_total` 已经是 1，直方图的 `_sum` 还是 0；会话 1 第 4 轮结束后，`_sum` 变成 1。第二次运行也一样，被抢占的还是会话 1 的第 4 轮，decode 用了 65.9 秒。第一篇里我写的是“哪个请求被抢占是从时间线推断的，日志里没有记录”，其实指标里有。

下面按时间顺序看。

## 第 3 轮：有空闲 block，也不放进来

第 3 轮的 4 条请求在 86 到 87 秒之间先后到达。会话 0 和会话 1 的先进了运行队列，两条 prompt 一共要 2,105 个 block（共用的 system prompt 那 17 个 block 只算一次）。prefill 算完时 KV 占用是 84% 左右，还空着约 400 个 block，之后两条请求 decode，又慢慢涨到 94%。

会话 2 第 3 轮的 prompt 是 14,746 个 token，命中了 system prompt 的 272 个。按第三篇和第四篇说的，prefill 每一步只算 2048 个 token，也只为这一步的 token 分配 block，第一块只要 128 个 block。空闲的 400 个 block 放得下第一块，它却在等待队列里等了 51 秒，直到前两条请求结束才开始算。这段时间里，`vllm:num_requests_waiting_by_reason{reason="capacity"}` 一直是 2。

原因是准入时的一条检查。等待队列里的请求要进运行队列时，调度器先按整条请求估算要多少个新 block，空闲 block 不够就整条不进，一个 block 也不分给它；够了才只分配这一步要用的 block。估算按 16 个 token 一个 block，减去已经被运行中的请求占着的命中 block。会话 2 第 3 轮要 922 个 block，命中的 17 个已经被另外两条请求占着，还要 905 个新 block；会话 3 第 3 轮要 966 个。空闲的只有 400 个左右，所以两条都进不来。

这条检查由启动参数 `--scheduler-reserve-full-isl` 控制，默认开着，`--no-scheduler-reserve-full-isl` 可以关掉，关掉后只看这一步要分配的 block 够不够。这两种设置我只用过默认的一种。

`capacity` 这个原因的意思是请求还在等待队列里、这一步没有被调度器主动跳过。整条放不下属于这一类；这一步的 token 预算已经被别的请求用完、运行中的请求数到了 `--max-num-seqs` 上限，也算这一类。另一个原因 `deferred` 是这一步被临时跳过的，比如 LoRA 适配器的数量限制、KV 传输还没就绪，这次实验里一直是 0。

## 第 4 轮：decode 把最后的 block 用完

第 4 轮还是一样，只能两条两条地进。会话 0 第 4 轮在 184.6 秒会话 2 第 3 轮结束后进来，prompt 21,072 个 token，要 1,317 个 block。会话 1 第 4 轮先到达等待队列，排在会话 2、3 的第 4 轮前面，会话 3 第 3 轮在 186.1 秒结束后，空闲 block 已经够它用了，但它又等了一秒多，到会话 0 的 prefill 算完才开始，这段时间卡住它的是每一步 2048 个 token 的预算，会话 0 的 prefill 每一步都把预算用完了。它的 prompt 是 16,984 个 token，要 1,062 个 block。

两条请求的 prefill 在 190 秒前都算完了，加起来是 2,362 个 block，还剩 132 个空闲。准入检查只估算了 prompt，没有估算还要输出多少 token。两条请求接下来各要再写 2000 个 token，会话 0 写完时要 1,442 个 block，会话 1 要 1,187 个，加起来比 2494 多出 118 个。

两条请求各自 decode，每写满 16 个 token 就要一个新 block，KV 占用从 94.7% 一点点往上涨。214.2 秒时是 99.92%，只剩 2 个空闲 block；下一次采样（214.8 秒）时抢占计数从 0 变成 1，运行中的请求从 2 个变成 1 个，等待中的从 2 个变成 3 个，KV 占用掉到 55.5%。

### 抢占在什么时候发生

抢占发生在一步开始时的调度阶段，还没有做前向。调度器先给运行中的请求分配这一步要用的 block，某一条 decode 要一个新 block、分不到的时候，就从运行队列里选一条请求抢占，收回它的 block，再给原来那条重新分配；还不够就再抢一条，直到分到为止。一步里可以连续抢占好几条。

### 被抢占的是谁

先到先服务时，被抢占的是运行队列里最后一条，也就是最晚进入运行队列的那条。会话 0 第 4 轮先进来，会话 1 第 4 轮后进来，所以被抢占的是会话 1 的。

要 block 的那条请求自己也可能被抢占：轮到它是运行队列里最后一条时，调度器就抢占它自己，这一步也不再调度它。这次是哪一条先分不到 block，从数据里看不出来；不管是哪一条，按这个规则被抢占的都是会话 1 第 4 轮。

用 `--scheduling-policy priority` 时，选的是优先级数值最大的，数值相同时选到达最晚的。

### 被抢占的请求交出了什么、保留了什么

{% include figure.html src="/assets/images/vllm-07-preemption/02-preempt.jpg" alt="左边的方框标着 running，里面有 session 0, turn 4 和 session 1, turn 4 两根横条，下方写 no free KV block；一条标着 preempt 的箭头从 session 1, turn 4 指向右边 waiting queue 方框里最靠前的竖条，箭头下方写 free its blocks, keep its output；waiting queue 里另有两根空白竖条，左下角写 front" caption="图 3：抢占时，运行队列里最后进来的请求交出全部 block，回到等待队列的最前面。左边画的是抢占前的运行队列" %}

被抢占的请求交出它占着的全部 block。和别的请求共用的 block（这里是 system prompt 那 17 个）只是引用计数减一，另一条请求还在用，不会被收回。抢占前后 KV 占用从 2,492 个 block 降到 1,385 个，少了 1,107 个，正好是会话 1 第 4 轮独占的 block 数：它这时一共有 1,124 个 block，也就是 17,969 到 17,984 个 token，已经输出了 1,000 个左右。

收回的 block 回到空闲队列，和第六篇第五步说的请求结束时一样：最后那个没写满的 block 放在队头，写满的 block 按从后往前的顺序放到队尾。写满的 block 哈希还在缓存表里，在被别的请求征用之前，仍然能被命中。

请求本身回到等待队列的最前面，已经算过的 token 数清零，下次调度时从头查缓存、重新计算。已经生成的 token 保留，不会重新采样，客户端也不会收到重复的输出，只是输出停了下来。

发生抢占的那一步，调度器不再从等待队列里接纳请求，刚被抢占的请求也不会在同一步被重新调度。

## 恢复：大部分不用重算

抢占之后，会话 0 第 4 轮一个请求单独 decode 了 20 秒，KV 占用从 1,385 个 block 涨到 1,442 个，多用的 57 个 block 从空闲队列的队头取。队头是会话 1 第 4 轮那个没写满的 block，之后是抢占前就空着的 2 个 block，再之后就是会话 1 第 4 轮留下的写满的 block，按放回的顺序，尾部的在前。所以被征用的是它最后 54 到 56 个满 block，大约 900 个 token，都在它已经生成的输出里；前面的 prompt 部分一个没动。

234.1 秒会话 0 第 4 轮结束，等待队列最前面的会话 1 第 4 轮先进来，会话 2 第 4 轮跟着进来。会话 1 第 4 轮查缓存时，查找的范围是 prompt 加上已经生成的 token，decode 时写满的 block 也算过哈希，同样能命中。按上面的推算，它命中前面 1,060 多个 block，只需要重算后面 900 个左右的 token，一步就算完了，算完下一步就接着 decode。这和普通请求的 prefill 没有区别，命中规则也和第六篇第二步一样，至少最后一个 token 要重算。

KV 占用的变化和这个推算对得上。会话 0 结束后的第一次采样（234.6 秒），KV 占用已经回到 1,325 个 block。会话 2 第 4 轮要算 16,535 个 token，一步 2048 个，花了大约 2 秒，一步约 0.25 秒；0.5 秒只够算两步，最多 4,096 个 token、256 个 block，1,325 个 block 里绝大部分只能是命中的。之后 KV 占用每 0.5 秒涨 256 个 block 左右，是会话 2 第 4 轮在 prefill，236.6 秒它出了第一个 token，这时 KV 占用是 2,163 个 block，正好是两条请求的 1,124 和 1,051 个 block 减去共用的 17 个，再加上会话 1 这两秒 decode 新写满的几个 block。

命中的前提是这些 block 还没被征用。这次被抢占的请求只等了 20 秒，这期间只有一条请求在 decode，用掉的 block 不多；如果等待期间有别的请求进来做 prefill，它留下的 block 会被大量征用，恢复时就要重算得多。

会话 3 第 4 轮还在等：会话 1 的第 4 轮恢复时，准入检查按 prompt 加已经生成的 token 一起估算，和会话 2 第 4 轮加起来是 2,158 个 block，再放会话 3 第 4 轮的 1,095 个就不够了。它要等到 258.4 秒会话 1 第 4 轮结束才进来。

## 这次抢占的代价

会话 1 第 4 轮的 decode 用了 68.6 秒，会话 0 第 4 轮是 46.4 秒，会话 2 第 4 轮是 48.7 秒，多出的 20 秒左右基本就是它在等待队列里的时间，重算的那 900 个 token 只占一步。第二次运行也一样，decode 用了 65.9 秒。

比起这次抢占，这个实验里等待的时间长得多。第 3 轮起的 8 条请求里有 6 条在等待队列里等了 50 秒以上才开始算，会话 3 第 4 轮等了 74 秒。准入检查让一部分请求等着，换来的是只发生了这一次抢占，其他请求一旦开始算就算到结束。这次抢占也正是因为准入时没有估算输出的长度：每轮只输出四五十个 token 时，decode 几乎不增长，第一篇里前两次实验就没有抢占。

## 从指标和日志看抢占

和抢占有关的指标，上面已经用到了：

- `vllm:num_preemptions_total`：计数器，每抢占一次加 1。
- `vllm:request_num_preemptions`：直方图，每条请求结束时记一次它被抢占的次数。桶从 1 开始，要分辨有没有被抢占，看 `_sum` 和 `_count`。
- `vllm:num_requests_waiting_by_reason`：等待中的请求数，按 `capacity` 和 `deferred` 两种原因分开。
- `vllm:kv_cache_usage_perc`：正在被请求引用的 block 占多少，抢占时会突然下降。

抢占发生时，vLLM 不打日志。第二次运行打开了 DEBUG 日志，整份日志里也找不到和抢占有关的行。每隔 10 秒的统计行在这个版本里也看不到抢占次数，要看抢占只能查 `/metrics`。两次运行里抢占前后的统计行，只看得出运行中和等待中的请求数、KV 占用的变化：

```text
Engine 000: Avg prompt throughput: 0.0 tokens/s, Avg generation throughput: 84.0 tokens/s, Running: 2 reqs, Waiting: 2 reqs, GPU KV cache usage: 98.7%, Prefix cache hit rate: 14.2%
Engine 000: Avg prompt throughput: 0.0 tokens/s, Avg generation throughput: 70.5 tokens/s, Running: 1 reqs, Waiting: 3 reqs, GPU KV cache usage: 56.0%, Prefix cache hit rate: 14.2%
```

## 只有重算

vLLM 0.32.0 的抢占只有一种做法：收回 block，以后重新计算。没有把被抢占请求的 KV 换出到 CPU 内存、恢复时再换回来的选项，也没有选择抢占方式的启动参数。把 KV 卸载到 CPU 内存是另一套机制，不在抢占这条路上，这次实验也没有开。

所以抢占的代价取决于恢复时还能命中多少。这次只重算了 900 个 token 左右；如果它留下的 block 在等待期间都被征用了，就要把 prompt 加上已经生成的约 18,000 个 token 全部重算一遍，按会话 2 第 4 轮的速度要 2 秒多。
