前两篇里反复出现几个数：每个 token 144 KiB，一个 block 2.25 MiB，5.48 GiB 能放 39,904 个 token。这一篇把它们从头算一遍，再和 vLLM 的指标、日志对上。例子还是那个编程智能体，看它最长的第 6 轮请求在 KV Cache 里占多少。

环境和前两篇相同。数据分别来自两台机器：`--gpu-memory-utilization 0.92` 的数字出自第一篇的实验，0.9 和其他配置的数字出自第二篇和后来的扩展实验。

## 第 6 轮请求占多少 KV

第 6 轮的 prompt 有 15,680 个 token，模型输出 29 个 token，请求结束时一共 15,709 个 token 的 KV 在显存里。

### 第一步：从模型结构算一个 token

KV Cache 存的是每一层 attention 的 K 和 V。一个 token 在一层里的 K 是 KV 头数乘以每个头的维数，V 也一样。模型目录里的 config.json 给出了需要的参数：

| 参数 | 值 |
| --- | ---: |
| 层数 `num_hidden_layers` | 36 |
| query 头数 `num_attention_heads` | 32 |
| KV 头数 `num_key_value_heads` | 8 |
| 每个头的维数 `head_dim` | 128 |
| 数据类型 | bfloat16，2 字节 |

一个 token 的 KV 是：

$$
2 \times 36 \times 8 \times 128 \times 2 = 147456 \text{ 字节} = 144 \text{ KiB}
$$

第一个 2 是 K 和 V 各一份，最后一个 2 是 bf16 的字节数。

Qwen3-8B 用的是分组查询注意力（GQA），32 个 query 头共用 8 组 K 和 V，所以公式里乘的是 8 而不是 32。如果 32 个头各有自己的 K 和 V，一个 token 就是 576 KiB，是现在的 4 倍；按 0.92 时的 5.48 GiB 算，只能放不到 1 万个 token，连一条 32768 token 的请求都放不下，服务根本起不来。

### 第二步：按 block 取整

vLLM 不按 token 分配 KV，而是按 block，一个 block 存 16 个 token。一个 block 号同时对应 36 层：每一层都有自己的一块 KV 张量，同一个 block 号在每一层里指向的都是这 16 个 token 的位置。所以一个 block 的大小是：

$$
16 \times 144 \text{ KiB} = 2304 \text{ KiB} = 2.25 \text{ MiB}
$$

第 6 轮的 15,709 个 token 是 981 个满 block，再加一个只装了 13 个 token 的 block，一共 982 个，合 2.16 GiB。最后一个 block 空着的 3 个位置也算占用，但每条请求最多浪费不到一个 block，相对两千多兆的总量可以忽略。

### 第三步：和指标对上

vLLM 的 `/metrics` 接口里有一个 `vllm:kv_cache_usage_perc`，表示 KV Cache 的 block 有多少比例正在被请求占用。第二篇第 3 次启动之后跑了一遍这 6 轮请求，那次是 0.9 的比例，KV Cache 一共 2280 个 block。回放脚本每 0.5 秒读一次这个指标，第 6 轮请求运行时读到的是 0.4305：

$$
0.4305 \times 2280 = 981.4
$$

和算出来的 982 个 block 对得上。

每轮请求一结束，这个指标就回到 0。请求结束后，它的 block 还给空闲池，内容还留着、下一轮还能命中前缀缓存（第一篇的第九步），但这个指标已经不把它们算作占用了。所以这个指标反映的是正在运行的请求占了多少，不是显存里还有多少可复用的缓存。

时间线上还能看到分块 prefill 时 block 是一段一段分出去的。第 2 轮请求运行时先后读到两个值：

| 读数 | 换算成 block | 对应的 token |
| ---: | ---: | --- |
| 0.1202 | 274 | 命中缓存的 288 个 + 前两块各 2048 个 = 4,384 个，正好 274 个 block |
| 0.1983 | 452 | 7,219 个 prompt token 加上开始 decode 后的几个 token，452 个 block |

第一篇说 prefill 分 4 步、block 按每一步实际要算的 token 分配，当时是推算的，这两个读数可以印证：前两步做完时只分到了 4,384 个 token 对应的 block，而不是一次分够 7,219 个。

## 一张卡能放多少

KV Cache 的总量在启动时就定了（第二篇的第七步），按 block 大小整除就是 block 数。前几篇几次启动的结果：

| 启动配置 | KV Cache | block 数 | token 数 |
| --- | ---: | ---: | ---: |
| 0.92，热启动 | 5.48 GiB | 2,494 | 39,904 |
| 0.9，热启动 | 5.01 GiB | 2,280 | 36,480 |
| 0.9，`--enforce-eager` | 5.43 GiB | 2,469 | 39,504 |
| 0.92，冷启动，`--max-model-len 16384` | 4.48 GiB | 2,041 | 32,656 |
| 0.92，EAGLE-3 投机解码，`--max-model-len 16384` | 3.08 GiB | 1,363 | 21,808 |

除了 EAGLE-3 那一行，其余的差别第二篇都讲过：比例不同，冷启动多扣了编译时的显存，`--enforce-eager` 不用扣 CUDA Graph 的预留。

EAGLE-3 这一行少得多，有两个原因。一是草稿模型的权重占了 1.9 GiB，留给 KV Cache 的显存少了。二是草稿模型自己也有 KV：它是 1 层 decoder，KV 头数和每头维数都和 Qwen3-8B 一样，每个 token 多出 $$2 \times 1 \times 8 \times 128 \times 2$$ 字节，即 4 KiB。每个 token 从 144 KiB 变成 148 KiB，一个 block 是 2.3125 MiB：

$$
\frac{3.08 \text{ GiB}}{2.3125 \text{ MiB}} \approx 1363
$$

正是日志里的 1,363 个 block。

## KV Cache 怎么限制最大长度

服务启动时，vLLM 会检查 KV Cache 能不能放下一条 `--max-model-len` 长的请求，放不下就直接报错退出。32768 个 token 需要：

$$
32768 \times 144 \text{ KiB} = 4.5 \text{ GiB}
$$

第二篇里两次冷启动都是卡在这里，报错里顺带给出了按现有显存能支持的最大长度：

| 启动配置 | KV Cache | 报错里给出的最大长度 |
| --- | ---: | ---: |
| 0.9，冷启动 | 4.01 GiB | 29,216 |
| 0.92，冷启动 | 4.48 GiB | 32,640 |

这两个数都是 16 的整数倍，分别是 1,826 和 2,040 个 block，也是按 block 算的。

反过来，Qwen3-8B 的 config.json 里 `max_position_embeddings` 是 40960。要支持这么长，一条请求要 5.625 GiB，0.92 热启动的 5.48 GiB 也不够，只能调高 `--gpu-memory-utilization` 或者换显存更大的卡。这个数是按公式算的，我没有在这张卡上启动 40960 验证。

启动日志里的另一项“Maximum concurrency”容易看错：

```text
GPU KV cache size: 39,904 tokens, Maximum concurrency for 32,768 tokens per request: 1.22x
```

1.22 只是 39,904 除以 32,768，意思是每条请求都用满 32768 个 token 时能同时放 1.22 条，并不限制同时运行的请求数。限制请求数的是 `--max-num-seqs`（默认 256）和实际的 block 数。智能体每轮只用一万多个 token，同时跑两三条也放得下；`--max-model-len` 改成 16384 那次，这个数变成了 1.99。

## 多个会话时

一个会话的第 6 轮只占 2,494 个 block 的 39%。第一篇里 4 个会话同时跑，最后一轮的 prompt 加起来是 52,069 个 token，按 144 KiB 算是 7.15 GiB，比 5.48 GiB 多出三成。实际运行时 KV 占用最高读到 0.985，也就是 2,456 个 block，当时有 3 个请求在跑，没有请求在等。4 个会话的最后一轮并不是同时开始的，正在跑的请求加起来没有超过总量。空闲 block 不够时会发生什么，放到第七篇讲。
