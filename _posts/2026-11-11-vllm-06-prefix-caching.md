第一篇的第四步说，调度器把 token 序列按 16 个一组切开，逐个 block 算哈希，到缓存里找内容相同的 block；第九步说，请求结束后写满的 block 不清空，下一轮还能命中。第五篇讲了命中的 block 怎样直接填进 block table、几条请求怎样共用同一组物理 block。这一篇把前缀缓存单独拿出来，跟着智能体的 6 轮请求看四件事：比对的是什么，新算出的 block 什么时候能被别人命中，显存不够时谁先被挤掉，以及第一篇留下的那个问题，为什么第 2 轮的 prompt 有 451 个满 block，第 3 轮却只命中 450 个。

行为以 vLLM 0.32.0 为准。单会话 6 轮和 4 个、8 个会话的数据来自第一篇的实验，`--gpu-memory-utilization` 0.92，2494 个 block；逐步调度日志那次 4 个会话（第四篇）、思考模式、工具调用和投机解码的对照是在第二篇那台机器上做的，单会话的 6 轮在第二篇那台机器上重跑过，每一轮的 prompt 长度和命中数都和第一篇一样。启动命令里都写了 `--enable-prefix-caching`，其实 0.32.0 对 Qwen3-8B 这类普通的生成模型默认就开着，不写也一样。

## 例子：6 轮请求各命中多少

第一篇单会话实验的 6 轮，加上每轮真正要计算的 token 数：

| 轮次 | prompt token | 命中缓存 | 要计算 | 首 token 时间 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 307 | 0 | 307 | 0.08 s |
| 2 | 7,219 | 288 | 6,931 | 0.83 s |
| 3 | 15,421 | 7,200 | 8,221 | 1.28 s |
| 4 | 15,536 | 15,408 | 128 | 0.14 s |
| 5 | 15,607 | 15,520 | 87 | 0.14 s |
| 6 | 15,680 | 15,600 | 80 | 0.13 s |

6 轮一共 69,770 个 prompt token，命中 54,016 个，占 77.4%。第 4 轮以后每轮只算一百个 token 上下，首 token 时间稳定在 0.14 秒左右；第 3 轮多读进一个大文件，要算 8,221 个 token，按第四篇看到的一步 2048 个 token 的预算，要分 5 步（这个步数是推算的），首 token 时间是 1.28 秒。

下面跟着第 3 轮请求走一遍。

### 第一步：进引擎时算出每个满 block 的哈希

请求进入引擎进程时，vLLM 就把 prompt 按 16 个 token 一组切开，给每个写满的 block 算一个哈希。第 3 轮的 15,421 个 token 是 963 个满 block，加上最后一个只有 13 个 token 的 block，后者不算哈希。

一个 block 的哈希由三样东西一起算出：前一个 block 的哈希、这个 block 自己的 16 个 token id、一组附加信息。附加信息包括 LoRA 适配器、多模态输入、请求里指定的 cache salt 和 prompt embeds，这里的请求都没有，这一项是空的。第 0 个 block 前面没有 block，用一个初始值代替。

因为每个 block 的哈希里含着前一个 block 的哈希，两个 block 的哈希相同，意味着从第 0 个 token 到这个 block 末尾的内容全都相同。同样 16 个 token，接在不同的前缀后面，哈希就不一样，不会被误当成同一段 KV。这和 KV 的性质一致：一个 token 的 K、V 取决于它前面所有的 token。

哈希算法默认是 SHA-256，可以用 `--prefix-caching-hash-algo` 换成 xxhash 等。用 SHA-256 时初始值是固定的（没有设置 `PYTHONHASHSEED` 的情况下），同一段 prompt 在服务重启后算出的哈希和重启前一样；xxhash 的初始值每次启动随机生成。显存里的缓存本来就不跨重启保留，但以后把 KV 卸载到内存或 SSD、在重启或多个实例之间复用时，哈希能不能对上就有关系了。

请求在 decode 时每写满一个 block，也会给它补算哈希。

### 第二步：从第 0 个 block 往后查，第一个不同就停

调度器第一次调度这条请求时查缓存：从第 0 个 block 开始，拿哈希去缓存里找，找到就看下一个，第一次找不到就停。因为哈希是一环套一环的，前面断了，后面的 block 即使内容相同哈希也不同，查下去没有意义。

第 3 轮查到第 450 个 block（从 0 数）时没找到，停了，命中的是前面的 450 个，即 7,200 个 token。

查找还有一个上限：最多命中 prompt 长度减 1 个 token，再向下取整到整 block。模型至少要对 prompt 的最后一个 token 做一次前向，才能拿到第一个输出 token 的概率分布，所以哪怕整段 prompt 都在缓存里，最后一个 token 也得重算；按整 block 取整之后，实际重算的是最后一整个 block。后面“同一段对话再发一次”一节有实测的例子。

### 第三步：命中的 block 直接用，只为剩下的分配

命中的 450 个 block 直接按顺序填进这条请求的 block table（第五篇第一步），引用计数加一，KV 不复制、不重算。剩下的 8,221 个 token 和第一篇讲的一样，按每一步的预算分块 prefill，每一步只为这一步要算的 token 分配新 block。

如果这时空闲 block 不够，请求留在等待队列里。这次查到的命中不会被保留下来：引用计数没有加上，那些 block 还在空闲队列里，照样可能被别的请求征用；下一次调度时重新从头查一遍，被征用掉的就命中不了了。

### 第四步：每算完一块就登记，不等请求结束

新算出的 block 不是等请求结束才进缓存。prefill 时，调度器给这一步分配 block 的同时，就把这一步会写满的 block 按哈希登记进缓存表，这时这一步的前向还没开始；decode 写满的 block，在默认的异步调度下，等这一步的输出处理完就登记。只登记写满的 block。

所以一条请求还在跑，它前面已经写满的 block 就能被同时到达的另一条请求命中。第五篇里会话 1 的第 1 轮命中 system prompt 的 17 个 block 时，会话 0 的第 2 轮还在 prefill，两条请求同时引用这 17 个 block。

### 第五步：请求结束，block 回到空闲队列

第 3 轮输出 55 个 token 后结束。它的 block 引用计数减到 0，回到空闲队列，但写满的 block 哈希还在缓存表里，KV 也没动。空闲队列有两头：

- 没有哈希的 block（每条请求最后那个没写满的）放到队头，下次分配最先拿走；
- 有哈希的 block 放到队尾，而且是按请求里从后往前的顺序放，请求的最后一个 block 先放、离队头更近。

分配新 block 时从队头取。取到的 block 如果还挂着旧哈希，就把这个哈希从缓存表里删掉，这个 block 的缓存到此失效。所以先被挤掉的是更早结束的请求留下的 block，同一条请求里先挤掉尾部，前缀留得更久。

第 4 轮到达时，第 3 轮留下的 963 个满 block 都还在空闲队列里。命中的 block 会从空闲队列里取出来、引用计数加一，第 4 轮命中了全部 963 个，15,408 个 token。

## 少命中的那个 block

第 2 轮的 prompt 有 451 个满 block，第 3 轮只命中 450 个；第 3 轮的 prompt 有 963 个满 block，第 4 轮却全部命中了。把每一轮的 prompt 长度除以 16 看余数：

| 上一轮 | 上一轮 prompt | 除以 16 的余数 | 上一轮的满 block | 下一轮命中的 block |
| --- | ---: | ---: | ---: | ---: |
| 1 | 307 | 3 | 19 | 18 |
| 2 | 7,219 | 3 | 451 | 450 |
| 3 | 15,421 | 13 | 963 | 963 |
| 4 | 15,536 | 0 | 971 | 970 |
| 5 | 15,607 | 7 | 975 | 975 |

余数是 0 和 3 时少命中一个 block，余数是 7 和 13 时一个不少。第一篇里我写的是“每一轮都比上一轮的 prompt 少命中一个 block 左右”，按这张表，5 次里是 3 次。

原因第一篇已经找到了，在 Qwen3 的对话模板：关闭思考模式时，模板在生成提示的末尾补一段空的思考标签 `<think>\n\n</think>\n\n`；下一轮把模型的回复当作历史重新渲染时，助手消息里只有回复内容，没有这段标签。两轮的 token 序列从这段标签的第一个 token 起就不同了。这段标签是 prompt 的最后几个 token，它们落在哪个 block 里，决定了少不少命中一个 block：如果整段都在最后那个没写满的 block 里，前面的满 block 全部能命中；如果有一部分落进了最后一个满 block，这个满 block 的哈希就对不上了。

{% include figure.html src="/assets/images/vllm-06-prefix-caching/02-mod16.jpg" alt="上下两行各画 prompt 的最后两个 block。上一行余数为 3，浅蓝的 4 think tokens 跨在两个 block 的交界处，左边写满的 block 标着 full block lost；下一行余数为 13，4 think tokens 完全在最后一个没写满的 block 里，左边的 block 标着 full block hit；标签右边的虚线部分是还空着的位置" caption="图 2：空思考标签是 prompt 的最后 4 个 token。余数小于 4 时它有一部分落在最后一个满 block 里，这个 block 下一轮命中不了。长度不按比例" %}

标签有几个 token，可以从数据反推。用 `tools` 字段做工具调用的那组实验里，prompt 长度除以 16 余 3 的那一轮之后少命中了一个 block，余 4 的那一轮之后没有少，所以标签正好是 4 个 token：`<think>`、两个换行、`</think>`、两个换行，两个换行是一个 token。规律就是：上一轮 prompt 长度除以 16 的余数小于 4，下一轮少命中一个 block。按这个规律算出的命中数，和关闭思考模式的各次实验里没被挤掉的轮次都对得上，包括后面多会话的几十个请求。

少命中一个 block 只是多算 16 个 token，对首 token 时间几乎没有影响。另外，从标签开始往后都对不上，模型上一轮的回复本身每一轮都要重新算，这个智能体每轮的回复是 30 到 55 个 token。

打开思考模式做对照时，6 轮的命中数都正好是上一轮 prompt 的满 block 数，一个不少：

| 上一轮 prompt | 下一轮命中 |
| ---: | ---: |
| 303 | 288 |
| 7,362 | 7,360 |
| 15,653 | 15,648 |
| 15,847 | 15,840 |
| 16,049 | 16,048 |

思考模式下生成提示只到“助手开始回复”的标记为止，模型自己输出思考标签和思考内容；下一轮的历史里只放回复，不放思考内容，两边从模型输出的第一个 token 起才不同。不过模型每轮几百到一千多字的思考内容不进入下一轮的历史，这部分 KV 也就用不上。

## 同一段对话再发一次

第一篇的 4 个会话实验是紧接着单会话实验在同一个服务上跑的。会话 0 的前两轮和单会话的前两轮 prompt 一模一样，命中的是单会话留下的 block：

| 请求 | prompt token | 满 block | 命中 |
| --- | ---: | ---: | ---: |
| 会话 0 第 1 轮 | 307 | 19 | 304（19 个 block） |
| 会话 0 第 2 轮 | 7,219 | 451 | 7,216（451 个 block） |

这次连思考标签所在的 block 也命中了，因为上一次那条请求的 prompt 里也有同样的标签。缓存只认内容，不管是哪条请求、哪个会话留下的。

prompt 长度正好是 16 的整数倍时，能看到第二步说的上限。工具调用那组实验把同一个 6 轮会话原样跑了两遍，第二遍每一轮都和第一遍同一轮的 prompt 完全相同，一共 70,417 个 prompt token 命中了 70,368 个。其中第 6 轮的 prompt 是 15,744 个 token，正好 984 个 block，全部在缓存里，命中的却是 15,728 个，983 个 block。最多命中 15,743 个 token，取整后是 983 个 block，最后一整个 block 的 16 个 token 重算。

## 多个会话时缓存被挤掉

单会话时，每一轮要命中的都是上一轮刚结束时留下的 block，中间没有别的请求来征用，所以命中数完全由上面那条规律决定。多个会话同时跑时就不一定了。

第四篇那次 4 个会话每隔 2 秒启动一个，是在一个刚启动的服务上做的。按“上一轮 prompt 长度减 4，向下取整到 16 的倍数”算出每一轮不被挤掉时应该命中多少，再和实际命中比，24 个请求里有 7 个少了：

| 请求 | 不被挤掉时应命中 | 实际命中 | 首 token 时间 |
| --- | ---: | ---: | ---: |
| 会话 3 第 3 轮 | 3,584 | 1,008（63 个 block） | 3.57 s |
| 会话 2 第 4 轮 | 10,816 | 272（17 个 block） | 2.69 s |
| 会话 3 第 4 轮 | 11,792 | 848（53 个 block） | 3.25 s |
| 会话 0 第 5 轮 | 15,536 | 13,120（820 个 block） | 1.51 s |
| 会话 1 第 5 轮 | 13,104 | 2,368（148 个 block） | 1.78 s |
| 会话 0 第 6 轮 | 15,616 | 4,768（298 个 block） | 4.21 s |
| 会话 1 第 6 轮 | 13,168 | 2,064（129 个 block） | 3.34 s |

首 token 时间里还包括排队，不全是重算的时间。整个实验不被挤掉的话应该命中 77.2%，实际是 51.0%，要计算的 token 从 51,516 个变成了 110,684 个。

这些被挤掉的请求，命中的都是开头一段，少的是后面。按第二步的查法，命中本来就只能是从头开始的一段；而前面能留下这么多，是因为第五步说的放回顺序：同一条请求的 block 尾部离队头更近，先被征用。会话 0 第 6 轮还命中了 298 个 block，它上一轮留下的 976 个满 block 里，后面 678 个已经分给了别的请求。

每一轮至少都命中了 272 个 token，也就是 system prompt 所在的 17 个 block。4 个会话的每一条请求开头都是这 17 个 block，它们不断被新请求命中，命中时从空闲队列里取出，请求结束时再放回队尾，总是刚用过的，排不到队头。

第一篇里 8 个会话每隔 0.5 秒启动一个，情况更极端。48 个请求不被挤掉的话应命中 77.2%，实际只有 11.2%：从第 3 轮起几乎每个请求都只命中这 17 个 block，最后两个请求到达时别的会话都已结束，才又命中了 11,088 和 15,792 个。那次等待队列里最多有 6 个请求，按第三步的说法，请求在等待期间不占住它查到的 block，等到真正被调度时，上一轮留下的 block 早已被征用了。

## 投机解码时少一个 block

第三篇提到过用 EAGLE-3 投机解码的那次启动（`--max-model-len 16384`）。在它上面跑同样的 6 轮，输出和不开投机解码时一样，prompt 长度完全相同，但每一轮的命中都少了正好 16 个 token：

| 轮次 | prompt token | 命中（不开） | 命中（EAGLE-3） |
| --- | ---: | ---: | ---: |
| 2 | 7,219 | 288 | 272 |
| 3 | 15,421 | 7,200 | 7,184 |
| 4 | 15,536 | 15,408 | 15,392 |
| 5 | 15,607 | 15,520 | 15,504 |
| 6 | 15,680 | 15,600 | 15,584 |

“不开”一列是同样 `--max-model-len 16384` 的对照启动。vLLM 0.32.0 在 EAGLE 一类方法（eagle、eagle3、mtp 等）下，查到命中之后再退回一个 block，这是在第二步那个上限之外另减的。源码注释给的原因是，草稿模型需要目标模型在生成位置之前那些 token 上的隐藏状态，要重算这一段才能得到。ngram 方法不在此列，命中数和不开时一样。

## 从指标看命中率

`/metrics` 里有两个计数器：`vllm:prefix_cache_queries_total` 是查询的 token 数，`vllm:prefix_cache_hits_total` 是命中的 token 数。每条请求在第一次成功分到 block、开始计算时统计一次，查询数是它的 prompt 长度，命中数和返回结果里的 `cached_tokens` 相同；因为 block 不够而留在等待队列里的那几次尝试不统计，被抢占后重新调度时的再次查询也不计入这两个计数器。单会话实验结束后两者分别是 69,770 和 54,016，和上面表里的合计一致。

引擎每隔 10 秒打一行统计日志，末尾的命中率是最近 1000 条请求的，不是从启动以来累计的：

```text
Engine 000: Avg prompt throughput: 16.7 tokens/s, Avg generation throughput: 8.0 tokens/s, Running: 0 reqs, Waiting: 0 reqs, GPU KV cache usage: 0.0%, Prefix cache hit rate: 77.4%
```

这几次实验每个服务上都不到 1000 条请求，日志里的值和用两个计数器算出来的一样。

第三篇说过，`vllm:kv_cache_usage_perc` 只算正在被请求引用的 block，请求结束后就回到 0。显存里还留着多少可命中的缓存，这两个指标都看不出来，只能从下一轮的命中数间接看。

做对照实验时有时需要清空缓存。`vllm serve` 有一个 `POST /reset_prefix_cache` 接口，只有设置了环境变量 `VLLM_SERVER_DEV_MODE=1` 才会开放：

```bash
VLLM_SERVER_DEV_MODE=1 vllm serve Qwen/Qwen3-8B --served-model-name qwen3-8b --max-model-len 32768
curl -X POST localhost:8000/reset_prefix_cache
```

有请求正在运行时，默认不会清空，返回 `{"success": false}`；加上查询参数 `reset_running_requests=true` 会先把运行中的请求抢占回等待队列再清空。这个接口我在实验里没有用过，上面的行为以 0.32.0 的源码为准。
